### Authentication
- `Register-OctoCliContext` - Unified login for all installations defined under `installations[]` in `~/.config/octo-tools/installations.json` (`-Installation <name>`, `-IncludeReporting`, `-IncludeAi`, `-UriSuffix`, `-NoSwitch`, `-NoLogin`, `-Json`; `-TenantId` takes a list `a,b,c` and then registers one context per tenant without switching the active context, logging each new context in by name). The cmdlet looks the installation up by name and builds the service URIs from the configured `services.*` URL templates (`{0}` is substituted with `-$UriSuffix`). See `docs/installations-config.md` for the config schema. Replaces the removed per-environment login helpers.

- `Invoke-OctoTenantSweep -CliArguments '-c','<Command>',... (-Installation <i> | -ContextTemplate <t> | -Context <c>) (-Tenant a,b | -AllTenants) [-Exclude ..] [-WhatIf] [-ShowOutput] [-IncludeOutput] [-Json]` - Supported replacement for scripts that copied tokens out of the octo-cli context file. Thin loop around `octo-cli --context <name> -c ...`: one context per tenant (`<inst>_{tenant}`) or one context with `{tenant}` in the arguments; octo-cli does the per-tenant authentication/exchange (octo-cli >= 3.5.27, checked). Result row per tenant (Ok/Denied/Failed, exit code, cause); a denied tenant (not provisioned: `ProvisionCurrentUser -ttid <tenant>`) does not stop the sweep. Never reads, prints, logs or writes a token, never opens the context file, never changes the active context; token-shaped text is scrubbed from all output. `-IncludeOutput` adds the scrubbed stdout per row, e.g. the response of `octo-cli -c GraphQl -tid {tenant} -q ...`, which replaces the GraphQL curl/Python scripts. Tests: `tests/OctoTenantSweep.Tests.ps1`. Details: `docs/tenant-sweep.md`.

### Identity Overlays
- `Invoke-IdentityOverlay` - Fans `octo-cli -c ApplyClientOverlay` across the blueprint-managed clients listed in an overlay YAML file (default: `overlays/identity-local-dev.yaml`). Idempotent — re-running on the same DB is a no-op (server dedupes against existing URIs). Per-client log lines show Added/SkippedDuplicate counts. Add `-DryRun` to print the invocations without calling out. Uses the active octo-cli context (login first with `Register-OctoCliContext -Installation local` or similar). Standalone today; Start-Octo wiring (`-SkipOverlay` opt-out) lands in a follow-up. Concept: `octo-platform-services/docs/concepts/phase-3-followup-identity-local-dev-overlay.md` §4.3.

### Cluster Access (Rancher / Break-Glass)
Two paths for Kubernetes access to Rancher-managed clusters:
- `Get-RancherKubeConfig -Cluster <name>` - Routine access with the token user's own permissions. Fetches a kubeconfig via the Rancher v3 API using your personal `RANCHER_API_TOKEN` and merges it into `~/.kube/config`. The resulting kubeconfig inherits whatever permissions the token user has. Requires `RANCHER_URL` (populated from `rancher.url` in your octo-tools config, or set in the private profile) and `RANCHER_API_TOKEN` (always set in the private profile, format `token-xxxxx:secret`, created in Rancher UI -> Account & API Keys).
- `Request-BreakGlassKubeConfig -Cluster <name> -Reason "..." -DurationHours <1-4>` - Write access for incidents. Triggers a Semaphore playbook that provisions a short-lived `cluster-admin` ServiceAccount token via Vault response-wrapping, with audit entries in Semaphore, Vault, the K8s audit log, and your operations chat channel. The token TTL closes the window automatically. Needs the Semaphore URL, break-glass project id and template id (the `semaphore.*` block of your octo-tools config or the matching `SEMAPHORE_*` environment variables) and your personal `SEMAPHORE_API_TOKEN` (environment only); the Vault address (`vault.addr`) is optional, the cmdlet has a default (see `docs/installations-config.md`).

This cmdlet pair assumes your clusters do not bind a persistent `cluster-owner` to any AD group — write access goes through the break-glass flow only.
