### octo-devstack (local stack daemon)
octo-devstack (the folder `devstack/` of this repository; formerly the private repo `meshmakers/octo-devstack`, now retired; its own `devstack/CLAUDE.md` holds its build, test and architecture notes) is the local MCP daemon that runs the OctoMesh dev stack for several Claude Code sessions (MCP `http://127.0.0.1:5090/mcp`, status page `http://127.0.0.1:5090/`, `GET /health`); it starts and stops the OctoMesh services itself (not a replacement for `Start-Octo` in a shell). Getting it reuses the existing cmdlets; module `modules/OctoDevStack.psm1`, tests `tests/OctoDevStack.Tests.ps1`.
- Location: `Start-OctoDevStackDaemon` / `Install-OctoDevStackDaemonService` default to `<this octo-tools>/devstack` (`-Path` for another; install and run the shared daemon only from the main octo-tools checkout (`-Path` picks another folder); never from a worktree (`wt-*`, `.claude/worktrees`) - a worktree of octo-tools has its own `devstack/`, and `Remove-OctoEnvironment` deletes it); the daemon takes the octo-tools checkout that holds its `devstack/` folder (unless `--octo-tools` / `OCTO_TOOLS_PATH`). `Get-OctoBuildOrder` skips `octo-tools` (and a leftover `octo-devstack` clone) and `Invoke-KillDotnet` never stops the daemon (`octo-devstack.dll`). Update with `git pull` of octo-tools, then `Start-OctoDevStackDaemon -Restart -Rebuild`
- `Start-OctoDevStackDaemon [-Path] [-Port 5090] [-Foreground] [-HealthTimeoutSeconds 30] [-Restart [-Force]] [-Rebuild] [-Json]` - Does nothing when octo-devstack already listens on the port; refuses another program on the port (names its PID); builds a missing `bin/Release/net10.0/octo-devstack.dll` with `Invoke-Build -configuration Release`; starts in the background (macOS/Linux: own process group via `/bin/sh` `set -m` + `nohup`, output appended to `~/.local/state/octo-devstack/daemon.log`; Windows: hidden `Start-Process`, previous log kept as `daemon.prev.log`) and waits for `/health`. The daemon inherits `OCTO_TOOLS_PATH` = this octo-tools checkout and asks it for the workspace (`Get-OctoWorkspace`; the variable is restored afterwards). `-Restart` stops a running daemon first with the rule of `Stop-OctoDevStackDaemon` (refused while builds run or wait, `-Force` overrides) and starts again; `-Rebuild` builds Release again before the start and is refused without `-Restart` while the daemon runs from those binaries. `-Json` adds `restarted`, `version`/`commit` (from `/health` of the daemon that answers), `restartSafe`, `blockers`, `warnings`, `refused`. Deploying a new octo-devstack commit to the shared daemon: `Start-OctoDevStackDaemon -Restart -Rebuild`. Register in Claude Code once: `claude mcp add --transport http --scope user octo-devstack http://127.0.0.1:5090/mcp`
- `Stop-OctoDevStackDaemon [-Port 5090] [-TimeoutSeconds 15] [-Force] [-Json]` - Stops only the listener on the port whose command line names `octo-devstack.dll` (macOS/Linux: lsof/ps, so `lsof` must be installed there; Windows: Get-NetTCPConnection/Win32_Process), never by name (without lsof the daemon names its own pid through `GET /api/daemon`, no second process scan here; so on Linux without lsof a daemon that does not answer `/api/daemon` - older, hung - is not found and nothing is stopped). The nominated pid must still pass the command-line check; there is no owner check of its own - a process of another user cannot be signalled anyway (`kill` fails with EPERM unless the cmdlet runs as root; accepted risk: a listener can name another octo-devstack of the same user). Asks the daemon first (`GET /api/daemon`, read-only; seam `Get-OctoDevStackDaemonStatus`): while `restart.safe` is false (a build runs or waits) nothing is stopped, the builds and their owners are named and `-Json` reports `refused: true`, `restartSafe: false`, `blockers`; `-Force` stops anyway (the builds go on, the next daemon re-attaches to them). Lease holders are a warning, never a refusal; a daemon without the endpoint (older version, or no answer) is stopped with a warning (`restartSafe: null`). macOS/Linux: SIGTERM, SIGKILL after `-TimeoutSeconds`; Windows: CTRL_BREAK through the daemon's own helper (`<dll> --send-ctrl-break <pid> <guard> console`, seam `Send-OctoDevStackCtrlBreak`; it signals the hidden console the daemon has to itself and refuses when anything else is attached), `Stop-Process -Force` after `-TimeoutSeconds` or when the helper refuses (an older daemon, a daemon in the foreground of a terminal). The helper is run only for a dll inside the octo-devstack checkout this octo-tools resolves (`Test-OctoDevStackTrustedDll`; any other dll - another account's, a copy elsewhere - is never executed, `Stop-Process` instead), with a timeout (10 s, killed after it), and never throws (`$false` = the fallback runs). `stopped` only after the process is gone; `-Json` `graceful` says whether it shut down by itself (under systemd from the unit's `Result`: `success` = true, another value = false, unknown = null). The stack services keep running and are adopted by the next start
- `Install-OctoDevStackDaemonService [-Path] [-Port 5090] [-NoStart] [-HealthTimeoutSeconds 30] [-Json]` / `Uninstall-OctoDevStackDaemonService [-Path] [-Json]` - Starts the daemon at login and after a crash on every OS, with `OCTO_TOOLS_PATH` = this octo-tools: Windows a scheduled task `\OctoMesh\octo-devstack` of the current user (at logon, repeated every 15 minutes, runs `Start-OctoDevStackDaemon` with the profile - it does nothing while the daemon answers); Linux a systemd user unit (`$XDG_CONFIG_HOME` or `~/.config`/`systemd/user/octo-devstack.service`, `KillMode=process` so a stop or restart never ends the stack services, `Restart=on-failure`, `SuccessExitStatus=75` - a daemon refused by the `daemon.lock` of another one exits with 75 and is not started again and again -, `OCTO_DEVSTACK_SERVICE=systemd`; then restart with `systemctl --user restart octo-devstack`); macOS a LaunchAgent `~/Library/LaunchAgents/io.meshmakers.octo-devstack.plist` (`KeepAlive`, `AbandonProcessGroup`, `dotnet <dll> --url <url>`, `OCTO_DEVSTACK_SERVICE=launchd`: its daemon waits for a held `daemon.lock` instead of exiting, KeepAlive would start it again every 10 s) written by the cmdlet (`Get-OctoDevStackLaunchAgentPlist`, pure, every value XML-escaped) and loaded with `launchctl bootout` + `bootstrap gui/<uid>`. All three in PowerShell, no shell script. systemd and launchd get `Get-OctoDevStackServicePathValue`: the installing shell's PATH without duplicates and missing folders, `~` expanded, a folder of the shell session (fnm's `fnm_multishells/<id>`) replaced by the folder it links to. Builds a missing Release build first. A daemon already running on the port is left alone (Linux: the unit is only enabled; macOS: refused, launchd would start a second one - the message names `Uninstall-OctoDevStackDaemonService` when the LaunchAgent runs it). Under systemd and launchd `started` is reported only once the daemon answers `/health` within `-HealthTimeoutSeconds` (both report a start before it is up; otherwise an error naming `daemon.log`). Writes and removals of the unit/plist stop on the first error (`-ErrorAction Stop`); `removed` is set only after the removal succeeded. Uninstall leaves the stack services alone; on macOS it goes through `Stop-OctoDevStackService` and keeps the plist when the job stays loaded after the bootout (error, `removed: false`). Service awareness of Start/Stop (`Get-OctoDevStackServiceState -Port`: `{kind, installed, supervised, pid, port, repoPath}`; supervised = launchd has the agent loaded, or the systemd unit is active (pid = its `MainPID`); `repoPath` = the checkout the definition launches (`WorkingDirectory` of unit/plist, `-Path` of the task, `Get-OctoDevStackServiceRepoPath`); the Windows logon task supervises nothing; only the service of the cmdlet's `-Port` counts - the `--url` of its unit/plist/`launchctl print`, `-Port` of the task, a definition without one counts for every port -, so a test daemon on another port is started and stopped as without a service and the service is left alone; `Test-OctoDevStackServiceRuns`: a listener is the service's daemon only when the manager names its pid - launchd without a pid (between two starts) never, systemd without a known `MainPID` when the unit is active; another pid = a daemon started by hand while launchd's waits for the state folder: Stop and `-Restart` stop it by its signal and launchd's takes over, `-Restart -Rebuild` is refused then before anything is stopped): `Start-OctoDevStackDaemon -Restart` restarts a supervised daemon through its service manager (`launchctl kickstart -k`, `systemctl --user restart`; with `-Rebuild`: stop through it, build, start through it, also after a failed build; when the old pid survives the stop nothing is built, an unloaded agent is loaded again and the run fails), same restart check, `-Json` `service`; under launchd/systemd the checkout built and started is the one of the definition (`repoPath`) - an explicit `-Path` naming another one is refused with the `Install-OctoDevStackDaemonService -Path` command that re-registers it as soon as something would be built, started or waited for (a daemon that already answers stays `alreadyRunning`); without a listener it waits for the service's daemon instead of starting a second one, and an installed service that does not run (the unit after a stop, the agent not loaded) is started through its service manager (`systemctl --user start`, `launchctl bootstrap`; not when no systemd user manager answers `systemctl --user show-environment` - WSL without systemd, a container -, not with `-Foreground`), never as a daemon of its own next to it. A daemon that exits at its start is reported with the last line of its log (`Get-OctoDevStackLastLogLine`: on a held `daemon.lock` it names the state folder). Before it starts or builds anything, a `daemon.lock` held in the state folder (a daemon on another port, or one still starting - the logon task can come by then) is refused (`-Json` `stateLocked`, `Test-OctoDevStackStateLocked`): the start would only end at the lock, and on Windows its log redirection would first truncate that daemon's log. `Stop-OctoDevStackDaemon` refuses under launchd (`refused: true`, names `-Restart` and `Uninstall-`), stops the unit with `systemctl --user stop` under systemd, and warns on Windows that the logon task starts it again. Seams for the tests: `Get-OctoDevStackServicePlatform`, `Register-/Unregister-OctoDevStackLogonTask`, `Get-OctoDevStackLogonTaskArguments`, `Invoke-OctoDevStackSystemctl`, `Get-OctoDevStackSystemdActive`, `Get-OctoDevStackSystemdShow`, `Test-OctoDevStackSystemdUserManager`, `Invoke-OctoDevStackLaunchctl`, `Get-OctoDevStackLaunchdDomain`, `Get-OctoDevStackLaunchAgentPath` - the test file mocks them at its root (no service runs), never call the cmdlets or a service manager unmocked from a test
- `Get-OctoWorkspace [-Json]` (module `OctoEnvironment.psm1`) - How this machine is laid out, for octo-devstack and other tools that must not assume a folder structure: `rootPath` (the folder holding the octo-tools checkout), `toolsPath`, `layout` (`lanes` | `flat` | null; `Get-OctoWorkspaceLayout`, root and default lane compared case-sensitively on Linux), `defaultLane` (as `Resolve-OctoEnvironmentDefaultBase`: `$env:OCTO_ENVIRONMENT_BASE`, else `branches/main` when it holds a lane, else `.`), `defaultLanePath`, `defaultLaneSource` (`setting` | `lanes` | `flat`), `environmentsRoot` (`<rootPath>`, environments are `wt-<env>` there), `configDirectory` (the folder of `Get-OctoToolsConfigPath`, absolute also for a relative `$OCTO_TOOLS_CONFIG`; octo-devstack keeps `devstack.yaml` there), `toolsConfigPath`, `toolsConfigExists`, `problems[]` (no lane found, no `installations.json`). Never throws for a workspace without a lane. Tests: `tests/OctoEnvironment.Layouts.Tests.ps1`
