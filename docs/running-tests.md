### Running tests
Module `modules/OctoTests.psm1`, tests `tests/OctoTests.Tests.ps1` (canned TRX in `tests/fixtures/trx`, `dotnet` mocked). `Invoke-BuildRange` / `Invoke-BuildEnvironment` never run a test (`-includeTests` builds, `-verifyTests` compiles); this is the only test runner and the only taker of the test lock.
- `Invoke-OctoTestRun (-env <env> | -branch <lane>) -repo <name> [-project <names>] [-filter <dotnet test filter>] [-rerunFailed] [-build Auto|Always|Never] [-dockerLock Auto|Always|Never] [-lockTimeoutSeconds 1800] [-dockerCheck Refuse|Warn|Off] [-minDockerFreeMemoryGiB 3] [-dockerCpus 4] [-dockerMemory <size>] [-configuration DebugL] [-maxFailures 50] [-includePassed] [-maxPassed 200] [-EventsFile <file>] [-WhatIf] [-Json]` - Runs `dotnet test` per test project of one repository (csproj with `<IsTestProject>true`, a `Microsoft.NET.Test.Sdk` reference, a `TUnit` / `MSTest` reference (not `TUnit.Engine` alone), or `xunit.v3*` in an `<OutputType>Exe</OutputType>` project - octo-communication-operator's tests reference only TUnit; also from an unconditional `Directory.Build.props`; `-project` = csproj name, relative path or unique part; all projects run, also after a failure). `-repo` takes the name forms of `Invoke-BuildRange`; with `-env` the manifest's `path` decides the folder.
  - No full rebuild: `-build Auto` passes `--no-build` when the build is current (`Get-OctoTestBuildState`), otherwise `dotnet test` builds incrementally and `buildReason` says why: no `<AssemblyName>.dll` below `<project>/bin/<configuration>` or `<repo>/bin/<configuration>` (the reason adds when the project is not in the repo's solution: `-verifyTests` / `-includeTests` never compile such a project, e.g. octo-adapter-sap `SapNwRfc.Tests`), a source of the test project newer than it or of a referenced project (incl. the `Directory.Build.*` chain above it) newer than that project's output (sources of unreferenced projects do not count; MSBuild keeps the test dll when a reference changed only inside), a referenced project built after it (its dll next to the test dll older than its output: src-only range build; or its `obj/<cfg>/<tfm>/ref` reference assembly - rewritten only on an API change, unlike `refint` - newer than the test dll; a multi-targeted reference in the test dll's target framework), or (DebugL) a newer `<id>.999.0.0.nupkg` in the lane feed for a package in the project's `obj/project.assets.json` (entries of type `package` only - a project reference of the same name, which the repo's own build packs into the feed, does not count; an unreadable `project.assets.json` is not current)
  - Isolation as in `Invoke-BuildEnvironment`: the lane environment (`Get-OctoLaneBuildSettings`, per-repo `RestoreSources`); an in-place worktree gets `RestoreSources` / `RestorePackagesPath` / `OctoLocalCatalogRootPath` as global properties and credentials in an owner-only `RestoreConfigFile` (helpers of `OctoEnvironment.psm1`, called through `Invoke-OctoModuleFunction` - not copied). The process environment is restored afterwards
  - Results: `<lane>/logFiles/test-results/<repo>/<project>/<run>/` with `results*.trx` and `dotnet-test.log` (newest 10 runs kept) and `last-result.json` next to the run folders (every failed test name; replaced by each run of the project). `-Json` data: `success, exitCode, failedStep (lock|docker|build|tests), failedProject, error, environment, lanePath, repo, repoPath, inPlace, configuration, filter, rerunFailed, totals{total,passed,failed,skipped}, elapsedSeconds, lane, msbuildProperties, lock{required,path,acquired,waitedSeconds,staleRemoved,blockedBy}, resultsPath, projects[{project,path,state: passed|failed|error|noTests|noMatch|skipped|notRun,success,exitCode,docker,dockerReason,noBuild,buildReason,filters,rerunCount,total,passed,failed,skipped,durationSeconds,failedTests[{name,displayName,outcome,message,stackFrame,durationSeconds}],truncated,passedTests[],passedTruncated,errors,runner,note,resultsPath,trx[],logFile}]`. `failedTests` holds at most `-maxFailures` entries (`truncated`); `name` is `<class>.<method>` (no theory arguments), `message` at most 1000 characters, `stackFrame` the first stack line; `errors` = run-level TRX errors or, without a TRX, up to 10 error lines of the log (`state: error` = broken build or crashed host). Human output lists the failed tests first. A preflight failure returns `{success:false, exitCode:1, error, failedStep:"preflight", repo, totals, projects:[]}`
  - `-rerunFailed` runs only the failed tests of each selected project's `last-result.json` (`FullyQualifiedName=` clauses joined with `|`, operators escaped, combined with `-filter` as `(<filter>)&(..)`, split into several `dotnet test` calls of at most `-maxFilterLength` 6000 characters, TRX `results-<n>.trx`); projects without failed tests are `skipped`; no previous result at all is a preflight error. A run with `-filter` / `-rerunFailed` in which no test ran fails (`failedStep: tests`)
  - Docker-heavy projects - a `Testcontainers` / `Testcontainers.*` PackageReference in the project, a project it references (transitively) or an unconditional `Directory.Build.props`; `-dockerLock Always|Never` overrides - run under the machine-wide test lock: projects without Docker run first, the lock is taken before the first Docker project and released after the last. Lock taken by another run: wait up to `-lockTimeoutSeconds` (0 = no wait), then `failedStep: lock`, `lock.blockedBy` = the owner, the Docker projects `notRun`
  - Runner per project (`projects[].runner`: `vstest` | `mtp` | `ng`): `mtp` when the nearest `global.json` from the project up to the repository root has `test.runner = Microsoft.Testing.Platform` (octo-bot-services, octo-communication-operator, octo-communication-controller-services, octo-adapter-finapi: with the .NET 10 SDK the VSTest call runs 0 tests there). MTP call: `dotnet test --project <csproj> -c <cfg> [--no-build] --results-directory <run> [-p:..] -- --report-trx --report-trx-filename <name> [filter]` (xunit.v3: `--report-xunit-trx --report-xunit-trx-filename`; no `-nodeReuse:false`, it would reach the test application). Every `dotnet test` starts in the repository folder (`global.json` is read from the current folder up). MTP exit code 8 = no test ran. `dotnet test` starts in the folder of the `global.json` that decided the runner (the repository root without one). Not supported: a multi-target project on MTP (every target framework would write the same TRX file name)
  - `-filter` is passed in the filter language of the project's runner: VSTest and MSTest/NUnit on MTP take an expression (`--filter FullyQualifiedName~Name`), TUnit a tree-node filter (`--treenode-filter /*/*/ClassName/*`), xunit.v3 on MTP a query filter (`--filter-query /*/*/ClassName/*`). A filter starting with `/` is a tree/query filter. A project whose runner cannot take the given form is not started: state `noMatch`, the note names the form it takes. `-rerunFailed`: VSTest clauses as above; TUnit one tree-node filter per class `/*/<namespace>/<class>/(<method>|<method>)`; xunit.v3 on MTP `--filter-method <name>` per test; for the two MTP forms `-filter` is not combined with the rerun
  - States with a filter (`-filter` / `-rerunFailed`): a project in which no test ran is `noMatch` (success, note `no test matched the filter`) - no pre-listing, the run with `--no-build` is the cheapest reliable check, a stale project is still built first (name `-project` to avoid that); a run without a failed test and without an error then fails only when no test ran in any project (failed tests and errors fail it as always). Without a filter a project that runs no test is `noTests` and fails the run (`failedStep: tests`) - never green
  - `-includePassed [-maxPassed 200]`: `projects[].passedTests` (names as in `failedTests[].name`) and `passedTruncated`
  - Docker engine guard (only for runs with Docker-heavy projects, after the lock is taken): the test containers share the engine - on Docker Desktop one VM (here 15.6 GiB, 16 CPUs) - with the kind cluster of the local stack (about 6 GiB). `-dockerCheck Refuse|Warn|Off` (default `Refuse`) compares the engine's free memory (`docker info` MemTotal minus the usage of the running containers from `docker stats`) with `-minDockerFreeMemoryGiB` (default 3): too little = `failedStep: docker`, the Docker projects `notRun`, the message names the biggest containers; docker not reachable = `check: unavailable`, the run goes on. `-dockerCpus <n>` (default 4; 0 = none) and the opt-in `-dockerMemory <size>` (default none; 0 / `''` = none) limit every container Testcontainers starts during the run (label `org.testcontainers=true`, not ryuk; only containers created after the run took the lock, 5 s clock tolerance - docker has no notion of "this run", so label plus creation time stand in for it: a labelled container that existed before, or whose creation time cannot be read, is never changed) with `docker update --cpus .. --memory .. --memory-swap ..` from a background thread (`Start-OctoDockerLimiter`, one pass per second) - from outside the test code, so about a second after the container started; a process that sized itself to the whole VM at start keeps that size and is killed when it grows past the memory limit. That is why no memory limit is set by default: mongod sizes its WiredTiger cache to the whole VM at start, is OOM-killed (exit 137) under a memory limit set afterwards, and the integration tests then hang in database timeouts; a memory limit is safe only together with a bounded mongo cache set at container creation, and a run with `-dockerMemory` warns (`limits.memoryWarning`, human output `Write-Warning`). The same values are in the test process as `OCTO_TEST_CONTAINER_CPUS` / `OCTO_TEST_CONTAINER_MEMORY_BYTES` (the latter only with `-dockerMemory`) for fixtures that set limits at creation (`WithCreateParameterModifier`, see readme). `-Json`: `docker{required, checked, check: ok|warned|refused|unavailable|off, available, memoryGiB, cpus, usedGiB, freeGiB, minFreeGiB, containers[{name,memoryGiB}] (top 5), message, limits{cpus,memory,memoryWarning}, limited[{id,name,image,success,error}]}`. Tests mock `Invoke-OctoDocker` and `Start-/Stop-OctoDockerLimiter` - never the real engine
  - No per-test live progress (events are per project)
  - Frontend tests: a folder with `angular.json` and a `package.json` that has a `test` script (found below the repository, at most four levels deep, never in `node_modules`/`dist`) is a test project named after its folder (two workspaces in folders of the same name: the folder path relative to the repository with dots, e.g. `apps.web`; the search goes on below a workspace without a `test` script). `-WhatIf` lists the spec files of a rerun as `rerunFiles`. It runs `npx ng test --watch=false --reporters=junit --output-file=<run>/results.junit.xml --reporters=default` in that folder (`npm ci` first when it has no `node_modules`; seam `Invoke-OctoFrontendTest`), log `ng-test.log`; the JUnit report is read like a TRX (`Read-OctoJUnitFile`), a failed test's `name` is `<spec file> :: <test name>`. `-filter` goes to `ng test --filter` (a regular expression over suite and test names), `-rerunFailed` runs the spec files that held a failed test (`--include`). No Docker lock, `noBuild` is always false. A consumer app is resolved by its exact folder name in a lane (a git repository), or from the environment's manifest
- `Get-OctoTestLock [-Json]` - Who holds the machine-wide test lock: `{locked, stale, ownerAlive, path, owner{pid, processStartTime, since, heldSeconds, user, host, command, lane, environment, repo, projects}}`. The lock is one JSON file, `$OCTO_TEST_LOCK_PATH` or `<state>/octo-tools/locks/docker-tests.lock` (`<state>` = `$XDG_STATE_HOME` or `~/.local/state`; Windows `%LOCALAPPDATA%`), written under a private name and moved into place without overwrite. Stale = the owner pid is not running or runs with another process start time; the next run replaces a stale lock on its own
- `Remove-OctoTestLock [-WhatIf] [-Json]` - Removes the lock only when its owner process is gone; a live owner is refused (no `-Force`)
- `Enter-OctoTestLock -Run @{command;lane;environment;repo;projects} [-TimeoutSeconds] [-OnWait {..}]` / `Exit-OctoTestLock -Id <id>` - The lock itself, for other cmdlets that start containers; tests always pass `-LockPath` (never the real lock). A suite started by hand (plain `dotnet test`, Rider) takes the same lock: `$l = Enter-OctoTestLock -Run @{..}; try { dotnet test .. } finally { Exit-OctoTestLock -Id $l.Id }` (`$l.Acquired` false = `$l.Owner` holds it). Lock file contract for other callers (fields `schemaVersion, id, pid, processStartTime, since, user, host, command, lane, environment, repo, projects`; take = write the full object under another name, move it onto the path without overwrite; release = delete when `id` is yours; stale = pid gone or other start time, 2 s tolerance): `readme.md`, "Running tests"
