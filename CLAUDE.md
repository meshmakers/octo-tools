# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

OctoMesh is a data transformation platform that converts raw data into meaningful information. This repository contains PowerShell-based development tools for building, deploying, and managing OctoMesh infrastructure.

## Key Technologies

- **Primary Language**: PowerShell scripting
- **Platform**: .NET 10.0 microservices
- **Infrastructure**: a local kind cluster (`Install-OctoKubernetes`) with MongoDB, CrateDB and RabbitMQ is the only supported local infrastructure. The Docker Compose setup is deprecated, removal 2026-12-31 (AB#7141)
- **Frontend**: Angular — Data Refinery Studio (octo-frontend-refinery-studio)

## Architecture

The system uses a microservices architecture with:
- MongoDB replica set (3 nodes on ports 27017-27019) for data storage
- CrateDB cluster (3 nodes on ports 4201-4203) for distributed SQL
- RabbitMQ (ports 5672, 15672) for message queuing
- Multiple .NET microservices for business logic

## Common Development Commands

All commands require PowerShell and are available after loading the profile:
```powershell
. .\modules\profile.ps1
```

### Machine-readable output (`-Json`)
Most query/status/compare commands (and many action commands) accept a `-Json` switch that suppresses
the colored human output and instead writes a single JSON document to the success stream, so the result
can be parsed by scripts, CI, or agents (`... -Json | ConvertFrom-Json`, or `... -Json > out.json`).

Every `-Json` document shares the same envelope:
```json
{ "schemaVersion": 1, "command": "Get-AllGitRepStatus", "timestamp": "<ISO-8601 UTC>", "data": <command-specific> }
```
- Query/compare commands put their results in `data` (e.g. an array of repo statuses, build results, version-diff rows).
- Pure action commands put a `{ "success": <bool>, "exitCode": <int>, ... }` summary in `data`.
- Interactive/blocking commands (the `Invoke-OctoCliLogin*` logins, `Invoke-MongoPortForward`, `Start-Octo`)
  do **not** support `-Json` — a single-emit JSON contract is meaningless while they block on input.
- Secret-bearing commands (`Get-RancherKubeConfig`, `Request-BreakGlassKubeConfig`) emit only safe metadata
  (cluster/context/expiry) under `-Json`; they never include the kubeconfig or any token.

**Build event file (`-EventsFile <path>`, Invoke-Build / Invoke-BuildRange / Invoke-BuildAll)** - live progress for a caller (octo-devstack): one compact JSON object per line (UTF-8, no BOM, flushed per line; `Write-OctoBuildEvent` in `OctoJsonOutput.psm1`, never throws), `{"schemaVersion":1,"ts":"<ISO-8601 UTC>","command":"<cmdlet>","event":"<event>",...}`. Events: `plan` {repos:[{repo,mode}],count} (mode as in the plan: dotnet/script/frontend/zenon/none) · `repoStart` {repo,index (1-based),count} · `phase` {repo,phase: restore|build|tests|packages|purge} · `repoDone` {repo,index,count,success,seconds,buildSeconds,testSeconds,packageSeconds,copied,purged,logFile} (copied/purged = counts; BuildAll: null) · `done` {success,failedRepo,failedStep,elapsedSeconds}. Rules: a run that stops before its first `repoStart` (refusal, invalid arguments, missing folder, running services) writes only `done` (`failedStep: preflight`, `failedRepo: null`); once a repository started it always gets its `repoDone` before `done` - after a throw a `repoDone` with `success: false` and null durations/counts, and `done` names that repository and the running phase. Invoke-BuildAll stops before building when the lane cleanup (`failedStep: cleanup`) or the DebugL package purge (`purge`) fails, and stops after a repository whose package copy failed (`packages`). `done` is best-effort on Ctrl+C (the finally block may not run to the end). A relative `-EventsFile` resolves against `$PWD`. Nothing under `-WhatIf` / `-DryRun`; the `-Json` document is unchanged. Phases: Invoke-Build restore/build; Invoke-BuildRange build/tests/packages/purge; Invoke-BuildAll build (restore included)/packages.

The shared helpers live in `modules/OctoJsonOutput.psm1` (`Write-OctoJson`, `New-OctoActionResult`), loaded
first by `profile.ps1`. New cmdlets should reuse them rather than calling `ConvertTo-Json` directly (the
helper sets a safe `-Depth` so nested data isn't silently truncated).

### Building
- `Invoke-BuildAll` - Build all repositories (use `-configuration Debug` for debug builds). Full reset in DebugL: wipes `<lane>/nuget` and the `meshmakers.*/999.0.0` folders of every package cache the lane restores into (`Remove-OctoLaneNuGetPackages` / `Get-OctoRangePackageCaches`: isolated lane = `<lane>/.nuget-packages` only; a legacy lane = global cache, plus the lane cache when `-laneIsolation Off` meets a `RestorePackagesPath`), forces restore, builds tests. `-msbuildProperties` / `-msbuildPropertiesPerRepo` as below.
  - `-DryRun` prints the plan (build order, builder per repo, lane environment, per-repo RestoreSources override), the run environment and the kill scope without killing, deleting or building anything; combine with `-Json` for a machine-readable plan
  - Kills only the dotnet processes of its own lane (`Invoke-KillDotnet -branchRootPath <lane>`, twice in DebugL; never the shared build server, other lanes or a local daemon such as octo-devstack); `-skipKill` for callers that stop the lane's processes themselves. For the whole run `MSBUILDDISABLENODEREUSE=1` and `UseSharedCompilation=false` are set (restored afterwards), so no reused MSBuild node or compiler server keeps files locked. On Windows a DebugL run whose purge includes the global package cache (legacy lane, e.g. main) runs `dotnet build-server shutdown` right before the purge (compiler servers can lock `999.0.0` analyzer DLLs there; they restart on demand) - shown in `-DryRun`
  - Lane isolation (`-laneIsolation Auto|On|Off`, default `Auto`, `Get-OctoLaneBuildSettings`): a lane is isolated exactly when its `<lane>/Octo.User.props` declares `<RestorePackagesPath>` (every feature environment; main after `Initialize-OctoLaneUserProps -branch branches/main -AddRestorePackagesPath`). The user-level `NuGet.Config` plays no role. An isolated lane builds with `NUGET_PACKAGES=<lane>/.nuget-packages` and `MSBUILDDISABLENODEREUSE=1`; in DebugL, repos whose `Directory.Build.props` declares no `<RestoreSources>` (mm-common) additionally get `RestoreSources=<lane>/nuget;nuget.org`. Repos that declare one already restore DebugL from `<repo>/../nuget`, and a blanket env override would drop their own default feeds (Telerik in octo-report-services). A lane without the line keeps the legacy behaviour (shared `~/.nuget/packages`, no environment variables); once every lane has it, nothing purges `~/.nuget/packages` any more. The environment is restored after the run
  - Order: mm-* → fixed core order (distributedEventHub … communication-sdk … communication-controller-services) → `octo-plug-dilos` (publishes Dilos.Nodes for octo-adapter-weclapp) → remaining octo-* alphabetically. Defined once in `modules/OctoBuildOrder.psm1` (`Get-OctoBuildOrder`), shared with `Invoke-BuildRange`; edit the lists there, not in the cmdlets
- `Invoke-BuildRange -branch <lane> -from <repo> -to <repo> [-include ..] [-exclude ..] [-includeTests | -verifyTests] [-msbuildProperties @{..}] [-msbuildPropertiesPerRepo @{..}] [-purgeStaleCache] [-laneIsolation Auto|On|Off] [-repoPaths @{..}] [-feedPath <dir>] [-EventsFile <file>] [-WhatIf] [-Json]` - Fast partial DebugL rebuild of a slice of the same build order: `src/` projects only (temporary `.slnf`), no forced restore, `Copy-NuGetPackages -onlyChanged` after each repo (copies what `<lane>/nuget` lacks or holds in an older, different version - also packages from an interrupted earlier run or an IDE build; skips orphaned nupkgs of removed projects) and a per-package purge of only the rebuilt `999.0.0` packages from the lane's package cache. Same lane isolation as `Invoke-BuildAll` (isolated lane: `NUGET_PACKAGES=<lane>/.nuget-packages`, `MSBUILDDISABLENODEREUSE=1`, per-repo `RestoreSources`; the purged/checked cache follows the lane, see `Get-OctoRangePackageCaches`). Fails fast, prints per-repo timings, refuses while Start-Octo services run out of a repo in the range (`-stopServices` / `-ignoreRunningServices`; not detected on Windows - stop them first there). Reports cache `999.0.0` folders whose SHA-512 differs from `<lane>/nuget`; `-purgeStaleCache` deletes them. **Test projects are not compiled unless `-verifyTests` (compile, do not run) or `-includeTests`** - use one of them before every hand-off; a plain run prints a reminder. See the "Fast local loop" section in `readme.md`.
  - Private feeds for library worktrees (octo-devstack): `-repoPaths @{ '<repo>' = '<absolute folder>' }` builds that repo from the folder (e.g. a git worktree) at its build-order position (absolute; refused unless the folder exists, holds a `.sln`/`.slnx` or `src/` and is that repo: a worktree whose `.git` file points to `<repo>/.git/worktrees/..`, or a clone with a `.git` folder named like the repo; warning when it is not next to the lane's repos - `../nuget` of repos with own `<RestoreSources>` would be another feed); `-feedPath <dir>` (DebugL only) copies the packages into `<dir>` (created when missing, `Copy-NuGetPackages -nugetPath`) instead of `<lane>/nuget`, purges no package cache, keeps the caller's `NUGET_PACKAGES`/`RestoreSources` (no lane override), skips the stale-cache check and refuses `-purgeStaleCache`; with more than one dotnet repo in the range it is refused unless `-msbuildProperties` contains both `RestoreSources` (private feed first) and `RestorePackagesPath` (private cache); a relative `-feedPath` resolves against `$PWD`; `-Json` reports `feedPath` and `repoPaths`, `-WhatIf` shows both. Repos with their own `<RestoreSources>` and a lane `RestorePackagesPath` ignore the environment - pass them as `-msbuildProperties` when downstream repos of the range must restore from the private feed
  - `-EventsFile <file>`: progress events, see the `-Json` section
- `Invoke-BuildRange -externalRepoPaths @{ '<repo>' = '<folder>' }` - repositories that are not lane folders, placed in the build order like a lane folder of that name (`Get-OctoBuildOrder -additionalRepos`) and validated like `-repoPaths`; the caller passes their isolation via `-msbuildPropertiesPerRepo` (used by `Invoke-BuildEnvironment` for in-place worktrees)
- `-msbuildProperties @{..}` (Invoke-Build, Invoke-BuildAll, Invoke-BuildRange) - extra MSBuild global properties (`-p:`) for every repo of the run; they override project values. `-msbuildPropertiesPerRepo @{ 'octo-identity-services' = @{ OctoPublishCkModel = 'false' } }` (BuildAll, BuildRange) targets single repos - use that form for `OctoPublishCkModel`, a run-wide `false` keeps every CK model out of the local catalog (warning when it hits more than one repo)
- `Sync-OctoCkIntermediateVersions -repositoryPath <repo> | -ckPath <ck folder> [-localCatalogRoot <dir>] [-privateCatalogLocation pages:<url>|github:<o>/<r>@<b>|dir:<path>] [-ckc <octo-ckc>] [-WhatIf]` - AB#7974: publishes the private catalog's versions of the declared major that lie strictly between the newest local version below the declared one and the declared version into `<lane>/.octo/local-catalog` (byte-identical, ascending, `octo-ckc -c Publish -c LocalFileSystemCatalog -lcr`), for the ckLanguage 2 models below `<repo>/src`, so the local CK compile gate does not fail with `OCTO-CK203`. Reads the private catalog's Pages mirror (no token); unreachable = warning, nothing changed; failure = warning with the exact command. `Invoke-BuildAll`/`Invoke-BuildRange` run it before each repository in DebugL (`-skipCkSync` turns it off). The logic is a verbatim copy of the script block of `octo-pipeline-templates/templates/steps/ck-sync-intermediate-versions.yml` (`modules/scripts/Sync-CkIntermediateVersions.ps1`); change both together. Tests: `tests/CkIntermediateSync.Tests.ps1`
- `Get-OctoBuildOrder -branchRootPath <checkout>` - The build order shared by `Invoke-BuildAll` and `Invoke-BuildRange` (single source of truth: `modules/OctoBuildOrder.psm1`; edit the pinned list there, not in the cmdlets)
- `Invoke-Build -repositoryPath .` - Build a single repository
  - Same lane isolation as `Invoke-BuildAll` (also `Invoke-Publish`): the lane is the nearest folder above the repo holding `Octo.User.props`; an isolated lane (its `Octo.User.props` declares `RestorePackagesPath`) gets `NUGET_PACKAGES`/`MSBUILDDISABLENODEREUSE` and, in DebugL for repos without own `<RestoreSources>`, `RestoreSources`; restored afterwards. Outside a lane and in a legacy lane nothing changes. `-DryRun` prints the environment without starting dotnet; `-laneIsolation Auto|On|Off`
  - A failed `dotnet restore` stops the run (no build; `success: false` with the restore exit code). `-EventsFile <file>`: plan, repoStart, phase restore/build, repoDone, done
- `Initialize-OctoLaneUserProps -branch <lane> [-AddRestorePackagesPath] [-WhatIf] [-Json]` - Source of the per-checkout, uncommitted `<lane>/Octo.User.props` (imported by every repo's `Directory.Build.props`; sets `RestorePackagesPath=<lane>/.nuget-packages`, so Rider and plain `dotnet build` use the lane cache too, and the lane counts as isolated). Creates the file when missing; without the switch an existing file is only checked. `-AddRestorePackagesPath` adds the line to an existing file that lacks it (a new PropertyGroup before `</Project>`, everything else byte for byte, backup `Octo.User.props.bak` or `.<timestamp>.bak`; idempotent; a `RestorePackagesPath` with another value is never rewritten). Used once to give main its own cache: `Initialize-OctoLaneUserProps -branch branches/main -AddRestorePackagesPath` (the first restore afterwards extracts every package into `branches/main/.nuget-packages`)
- `Invoke-BuildAndStartOcto` - Build everything and start the application

### Feature environments (AB#8700)
An environment is a small, isolated lane at `<rootPath>/wt-<env>` and IS an octo-claude-pm lane: `<env>` is the lane name (lower-case, digits, `-`, e.g. `ab8625-enum-null` or `odysseus-kind`), `wt-<env>` its lane folder; environments are discovered by `<rootPath>/wt-*/.octo/environment.json` (flat worktrees `wt-<lane>-<repo>` have none). It holds git worktrees of the changed repos (role `feature`, on `<user>/AB#<id>_<desc>`) and of the repos to rebuild against them (role `consumer`, detached at the base checkout's commit), its own `nuget/` feed, `.nuget-packages/` cache, `.octo/local-catalog` and `.octo/local-blueprint-catalog`, `logFiles/`, an `Octo.User.props` (`RestorePackagesPath`, `OctoEnvironment`, `OctoEnvironmentBase`; imports the base lane's props for its other settings) and `.octo/environment.json` (schemaVersion 1: name, workItem, base, created, owner, repos[name, role, path, branch, baseCommit], slot - written only by octo-tools, read by octo-devstack). The folders keep the plain repo names, so `../nuget`, `../.octo/local-catalog`, `Find-OctoLaneRoot` and `Get-OctoBuildOrder` resolve inside the environment; plain `dotnet build`, Rider and `Invoke-Build` there are isolated without extra properties. `-branch wt-<env>` works in every lane cmdlet. The environment folder must not lie inside the base lane (refused), and a name whose `wt-<name>` already exists without a manifest (an octo-claude-pm lane folder or a flat worktree) is refused. The manifest's `path` is authoritative for every repo (in-place repos lie outside `wt-<env>`). Claims stay in the base lane, `branches/main/.octo/claims/<repo>.md`, with `Environment:` and `Worktree:` lines (format documented by octo-claude-pm); environments never create claims in their own folder. Module `modules/OctoEnvironment.psm1`, tests `tests/OctoEnvironment.Tests.ps1`. All cmdlets take `-env` and `-Json`.
- `New-OctoEnvironment -env <slug> -repos <names> [-workItem AB#..] [-branchName <git branch>] [-owner <text>] [-base branches/main] [-addAffected] [-WhatIf] [-Json]` - Creates the folder, the feature worktrees (an existing local/origin branch is checked out instead of created), props and manifest, and seeds feed and catalogs from the base lane (Sync rules). `-addAffected` adds every transitive consumer as a consumer worktree
- `Get-OctoEnvironment [-env <slug>] [-Json]` - Lists the environments; with `-env` also the git state of each worktree (exists, dirty, unpushed)
- `Add-OctoEnvironmentRepo -env <slug> -repo <name> [-role feature|consumer] [-addAffected] [-WhatIf] [-Json]` - Adds a worktree; `-addAffected` also adds, as consumers, the affected repos on the path from the feature repos to `-repo`
- `Add-OctoEnvironmentRepo -env <slug> -path <existing worktree> [-inPlace] [-role ..] [-WhatIf] [-Json]` - Adopts a linked worktree: an octo-claude-pm flat `<checkout>/wt-<lane>-<repo>` or a Claude Code `<repo>/.claude/worktrees/<name>` (repo = the owning main checkout, branch = its branch, baseCommit = merge base with the main checkout's HEAD; main checkouts are refused). Default: `git worktree move` to `wt-<env>/<repo>` (uncommitted changes move along; refused when git has it locked or a process runs from it - `Get-OctoProcessesUnderFolder` in `Invoke-KillDotnet.psm1`: the lane matching of Invoke-KillDotnet (cwd, entry assembly, modules), list-only over every process, so a shell, IDE or Claude Code session counts too; Windows cannot see working directories); reports `oldPath`/`newPath`. `-inPlace` only records it: `Invoke-BuildEnvironment` builds it from its folder with `RestoreSources=<env>/nuget;nuget.org`, `RestorePackagesPath=<env>/.nuget-packages` and `OctoLocalCatalogRootPath=<env>/.octo/local-catalog` as global properties, but **a plain `dotnet build` or Rider in an in-place worktree is not isolated** (it restores from the `../nuget` next to it). The `RestoreSources` passed for it are its `Directory.Build.props` evaluated for DebugL (`Get-OctoInPlaceRestoreSources`): the environment feed in place of `../nuget`, the repo's own sources (octo-report-services keeps Telerik; nuget.org when it declares none) and macros such as `$(OctoNugetPrivateServer)` substituted from the base lane's and the environment's `Octo.User.props` (a global property is not macro-expanded); a source with an unresolvable macro is dropped with a warning naming the macro. Credentials never reach the dotnet command line: `RestoreSources` carries the sources without them, an owner-only `NuGet.Config` in a temporary folder (mode 600 / current-user ACL, deleted after the build, also on failure) passed as `RestoreConfigFile` carries them plus the user-level `NuGet.Config`'s credentials for the same sources (e.g. Telerik), because `RestoreConfigFile` replaces that file. Feed URLs with credentials are masked in every output (`Hide-OctoUrlCredentials`). The environment's kill scope covers it. Remove only unregisters an in-place worktree, never deletes it (it belongs to its original owner)
- `Sync-OctoEnvironment -env <slug> [-WhatIf] [-Json]` - Snapshot refresh from the base lane, port of octo-devstack's `PrivateFeed` rules: missing packages copied, mirrored ones refreshed when the base changed, packages built in the environment always win; then `<env>/.nuget-packages/<id>/<version>` folders whose nupkg differs from the feed are purged. The catalogs follow the same rules; a `catalog.json` changed on both sides is JSON-merged (union by modelName/majorVersion or version, environment wins, latestVersion recomputed), a `cache/*-cache.json` changed on both sides is dropped. State in `<env>/.octo/sync/*.json`. `-Json` (also of `New-OctoEnvironment` and `Invoke-BuildEnvironment`) reports per feed/catalog the counts and at most 20 names per list (`truncated`); `-Detailed` lists every file. Never writes the base lane. Main's feed is copied, never added as a second source (same id/version in two local sources: NuGet takes whichever answers first)
- `Get-OctoAffectedRepos -env <slug> [-target <repos>] [-Json]` - Transitive consumers of the feature repos from a package graph of the base lane (environment worktrees replace their base folders): produced ids = packable csproj (`<PackageId>` or the project name; `<IsPackable>false</IsPackable>` produces nothing), edges = `<PackageReference Include="Meshmakers.*">` in csproj/props. Every csproj/props of the repo is read (projects outside `src/` count too); `node_modules`, `bin`, `obj`, `.git`, generated output (`dist`, `.angular`, `artifacts`, `coverage`, ...) and symlinks are never entered (about half a second for `branches/main`). `-target` keeps the repos on the path to the targets. Intermediate libraries must be rebuilt too, otherwise main's prebuilt packages bind to the new library at runtime (`MissingMethodException`)
- `Invoke-BuildEnvironment -env <slug> [-syncMain] [-verifyTests | -includeTests] [-EventsFile <file>] [-skipKill] [-DryRun] [-Json]` - Optional sync, then `Invoke-BuildRange -branch wt-<env>` from the environment's first to its last repo in the shared build order (frontends included; in-place worktrees via `-externalRepoPaths` at their position, with the global properties above via `-msbuildPropertiesPerRepo`). Packages land in `<env>/nuget`, the per-package purge hits only `<env>/.nuget-packages`. `-Json` returns Invoke-BuildRange's data plus `environment` and `synced` (and `sync`); events carry command `Invoke-BuildEnvironment` (`Invoke-BuildRange -EventsCommand`). `-DryRun` = `Invoke-BuildRange -WhatIf`, no sync. Use `-verifyTests` or `-includeTests` before every hand-off. Never publish feature work into `branches/main/nuget`
- `Remove-OctoEnvironment -env <slug> [-WhatIf] [-Json]` - Removes the worktrees and what the environment owns (feed, cache, catalogs, logs, props, manifest; anything else stays, the folder goes only when empty); in-place worktrees are only unregistered; refuses (removes nothing) when a worktree is dirty or has commits on top of its base commit that no remote has. No `-force`. Feature branches are kept. Stop the environment's services first (octo-devstack `env_remove` does it)
- Kill scope: `Invoke-KillDotnet -branchRootPath <rootPath>/wt-<env> -additionalRoots <in-place worktrees>` (run by `Invoke-BuildEnvironment` before the build, `-skipKill` to opt out; `-additionalRoots` = further git repositories/worktrees matched with the same lane rule); main's scope (`branches/main`) never matches `wt-<env>` (prefix with trailing separator), and `wt-<env>` never matches `wt-<env>-<repo>`. The CK intermediate-version sync of an environment without the engine uses the base lane's `octo-ckc` before `PATH`

### Infrastructure Management (docker-compose, DEPRECATED, removal 2026-12-31)
kind (`Install-OctoKubernetes`, below) is the only supported local infrastructure. Every cmdlet in this section and the backup cmdlets print a deprecation warning. `Start-/Install-OctoInfrastructure` never change the CrateDB image of existing volumes (`OctoComposeInfra.psm1`): they refuse when the data was written by another CrateDB version than the compose file pins (a record in `~/.config/octo-tools/compose-crate-version.txt` plus the images of existing `cratedb` containers; `Stop-` records it before the containers go, `Uninstall-` clears it; existing volumes of unknown version need `-AcceptUnknownCrateVolumes` once). Migration: `kubernetes/README.md`, "Migrating from docker-compose".
- Local RabbitMQ users (AB#7338): vhost `/`, `guest`/`guest` (full permissions, host services) and the restricted adapter user `octo-adapter-mq-user`/`adapter` (everything except resources whose name contains `octo::method::`, no write to `amq.default`) come from `infrastructure/rabbitmq/definitions.json` (compose mount and kind ConfigMap `rabbitmq-definitions`, created by `Install-OctoKubernetes`; an existing broker needs a restart to load it). Mirrors the clusters (meshmakers-infrastructure `docs/runbooks/rabbitmq-adapter-user.md`). Check: `infrastructure/scripts/verify-adapter-broker-user.sh [kind|docker[:name]]`.
- `Start-OctoInfrastructure` - Start Docker infrastructure (MongoDB, CrateDB, RabbitMQ)
- `Stop-OctoInfrastructure` - Stop Docker infrastructure
- `Install-OctoInfrastructure` - Initial infrastructure setup
- `Get-OctoInfrastructureStatus` - Check infrastructure status
- `Start-Octo` - Start the Octo application after infrastructure is running
- `Stop-Octo` - Stop services started in non-interactive mode (`Start-Octo -nonInteractive $true`)

### Local Kubernetes (Kind) dev environment
An alternative to the docker-compose infrastructure: MongoDB/RabbitMQ/CrateDB, the CRDs, and the Communication Operator run inside a local [kind](https://kind.sigs.k8s.io/) cluster (the core .NET services still run as host processes via `Start-Octo`). The two infra modes share the same host ports and **cannot run at the same time**. Full runbook: `kubernetes/README.md`; from-scratch setup: `kubernetes/QUICKSTART.md`.
- `Install-OctoKubernetes` - Create the kind cluster + CRDs + namespaces + in-cluster infra (incl. seeding the CrateDB application user `octo-system` that deployed adapters connect with, AB#5232) + ingress-nginx/cert-manager, then deploy the operator (idempotent; refuses while the docker-compose infra is up)
- `Update-OctoCrateDb` - Guarded CrateDB apply/upgrade of a kind cluster (AB#7139); `Install-OctoKubernetes` calls it instead of a plain `kubectl apply` of `infra/cratedb.yaml` (`-SkipCrateDbSnapshot` passes through). `-Context` is mandatory (never the current context). Fresh install: apply. Running version (`sys.nodes`) = manifest `image: crate:<x.y.z>`: no-op. Running newer than the manifest: error, manifest NOT applied (CrateDB cannot be downgraded). Older: free-disk check, snapshot into `path.repo` (`/data/backup`), then step by step (below 5.10.1 to 6.x via 5.10.16), after each step rollout + version + all tables GREEN + a row-count difference is a warning that names the tables; refuses a non-kind context, a volume without a StatefulSet (unless `-AssumeFreshCrateDbVolume`) and unknown major jumps. `-SkipSnapshot` / `-NonInteractive`. getting-started has the same logic as the standalone `scripts/om-upgrade-cratedb.ps1`; keep both in step
- `Initialize-OctoKindCrateDbUser` - Idempotently seed the CrateDB application user (`octo-system`, name/password read from `kubernetes/operator-dev-values.yaml`) in the kind CrateDB. Run once on clusters created before the seeding step existed — without it, adapter archive writes fail with `trust authentication failed for user "octo-system"`.
- `Deploy-OctoOperator` - (Re)deploy the Communication Operator standalone from the dev registry (`:main-latest`). Wires up trust for the host's TLS certificate on its own (no client in the cluster has a bypass — see `kubernetes/README.md`): read off the running controller, or exported from the ASP.NET dev-cert store when the controller is down (so `Install-OctoKubernetes` wires it correctly before `Start-Octo` ever ran, AB#5232). Also projects `authUri` on the certificate's SAN hostname plus `additionalValidIssuers` (`https://localhost:5003/`, from `operator-dev-values.yaml`) into every workload. `-SkipControllerTlsTrust` opts out. `-SkipRegistryCheck` deploys against an image already loaded into the node.
- `Get-OctoKubernetesStatus` - Show pods, Helm releases, host-port reachability and the local S3 store check for the kind cluster (`-SkipS3Probe` keeps it read-only)
- `Install-OctoKubernetesS3Store` / `Test-OctoKubernetesS3Store` / `Uninstall-OctoKubernetesS3Store` / `Set-OctoKubernetesCrateDbJobLogFilter` - The local S3-compatible object store (SeaweedFS, `octo-infra`, host `localhost:8333`, in-cluster `seaweedfs.octo-infra:8333`, bucket `octo-artifacts`) that the archive `COPY TO` / `COPY FROM` staging area uses (AB#5967), and the persistent CrateDB setting `stats.jobs_log_filter` that keeps `COPY` statements (they carry the S3 key) out of `sys.jobs_log`. `Install-OctoKubernetes` adds the store (`-SkipS3Store` to leave it out); `Install-OctoKubernetesS3Store` adds it to an existing cluster without touching anything else. The credential is generated once into the Secret `octo-infra/seaweedfs-s3` and exists nowhere else. `Start-Octo` hands the bot the S3 provider settings and the second endpoint CrateDB sees (`Set-OctoLocalS3StoreEnvironment`, `-s3Store $false` opts out). ### octo-devstack (local stack daemon)
octo-devstack (private repo `meshmakers/octo-devstack`) is the local MCP daemon that runs the OctoMesh dev stack for several Claude Code sessions (MCP `http://127.0.0.1:5090/mcp`, status page `http://127.0.0.1:5090/`, `GET /health`); it starts and stops the OctoMesh services itself (not a replacement for `Start-Octo` in a shell). Getting it reuses the existing cmdlets; module `modules/OctoDevStack.psm1`, tests `tests/OctoDevStack.Tests.ps1`.
- `Invoke-CloneMainRepos -devTools` - Clones `octo-devstack` into the folder that holds the octo-tools checkout (for an octo-tools worktree: that of the main checkout, where `Start-OctoDevStackDaemon` looks), never into a lane. `Get-OctoBuildOrder` skips `octo-tools`/`octo-devstack` and `Invoke-KillDotnet` never stops the daemon, also when that folder is used as a lane. Update with `git pull` in that folder
- `Start-OctoDevStackDaemon [-Path] [-Port 5090] [-Foreground] [-HealthTimeoutSeconds 30] [-Restart [-Force]] [-Rebuild] [-Json]` - Does nothing when octo-devstack already listens on the port; refuses another program on the port (names its PID); builds a missing `bin/Release/net10.0/octo-devstack.dll` with `Invoke-Build -configuration Release`; starts in the background (macOS/Linux: own process group via `/bin/sh` `set -m` + `nohup`, output appended to `~/.local/state/octo-devstack/daemon.log`; Windows: hidden `Start-Process`, previous log kept as `daemon.prev.log`) and waits for `/health`. `-Restart` stops a running daemon first with the rule of `Stop-OctoDevStackDaemon` (refused while builds run or wait, `-Force` overrides) and starts again; `-Rebuild` builds Release again before the start and is refused without `-Restart` while the daemon runs from those binaries. `-Json` adds `restarted`, `version`/`commit` (from `/health` of the daemon that answers), `restartSafe`, `blockers`, `warnings`, `refused`. Deploying a new octo-devstack commit to the shared daemon: `Start-OctoDevStackDaemon -Restart -Rebuild`. Register in Claude Code once: `claude mcp add --transport http --scope user octo-devstack http://127.0.0.1:5090/mcp`
- `Stop-OctoDevStackDaemon [-Port 5090] [-TimeoutSeconds 15] [-Force] [-Json]` - Stops only the listener on the port whose command line names `octo-devstack.dll` (macOS/Linux: lsof/ps, so `lsof` must be installed there; Windows: Get-NetTCPConnection/Win32_Process), never by name. Asks the daemon first (AB#8812, `GET /api/daemon`, read-only; seam `Get-OctoDevStackDaemonStatus`): while `restart.safe` is false (a build runs or waits) nothing is stopped, the builds and their owners are named and `-Json` reports `refused: true`, `restartSafe: false`, `blockers`; `-Force` stops anyway (the builds go on, the next daemon re-attaches to them). Lease holders are a warning, never a refusal; a daemon without the endpoint (older version, or no answer) is stopped with a warning (`restartSafe: null`). macOS/Linux: SIGTERM, SIGKILL after `-TimeoutSeconds`; Windows: `Stop-Process -Force` at once (no timeout). `stopped` only after the process is gone. The stack services keep running and are adopted by the next start

### Cleanup
- `Remove-BinAndObjFolders` - Remove all bin/obj folders
- `Invoke-KillDotnet [-branchRootPath <lane>] [-Json]` - Without `-branchRootPath`: `dotnet build-server shutdown` and kill every dotnet process (Windows only, no-op elsewhere). With `-branchRootPath` (lane mode, used by `Invoke-BuildAll` and `Sync-NuGetPackages`): only dotnet processes whose working directory (`lsof`, macOS/Linux), command line or (Windows) loaded module path lies under the lane folder - from the command line only the entry assembly (first `.dll`/`.exe` after the host, a relative one against the cwd), never other arguments; `-branchRootPath` resolves against `$PWD` and is refused unless it exists and holds `Octo.User.props` or an `octo-*`/`mm-*` folder. Windows stops them (no build-server shutdown), macOS/Linux only reports them. Returns `{pid, name, reason}`; `-Json` data `{killedCount, processes, scoped: true, buildServerShutdown: false}`
- `Remove-GlobalNuGetPackages [-path <cache>]` - Remove the local 999.0.0 Meshmakers packages from a NuGet package cache (default `~/.nuget/packages`). Each lane restores into its own cache, `<lane>/.nuget-packages`, configured via `RestorePackagesPath` in `<lane>/Octo.User.props`; `Invoke-BuildAll`/`Sync-NuGetPackages` use `Remove-OctoLaneNuGetPackages -laneSettings` instead, which cleans the caches of `Get-OctoRangePackageCaches`: an isolated lane (`RestorePackagesPath` in its `Octo.User.props`) only its own cache, never the global one; a legacy lane the global cache (plus its lane cache when `-laneIsolation Off` meets a `RestorePackagesPath`) - always only `meshmakers.*/999.0.0`. Without `-laneSettings` this cmdlet cleans just the given path
- `Copy-NuGetPackages -directory <repo> -branch main [-modifiedSince <time> | -onlyChanged] [-nugetPath <dir>]` / `Copy-AllNuGetPackages -branch main` - Copy DebugL packages into `<lane>/nuget` (`-nugetPath`: another target folder, e.g. a private feed) (Copy-All: newest file per package wins, duplicates are warned about, a newer package already in nuget/ is kept)

### Authentication
- `Register-OctoCliContext` - Unified login for all installations defined under `installations[]` in `~/.config/octo-tools/installations.json` (`-Installation <name>`, `-IncludeReporting`, `-IncludeAi`, `-UriSuffix`, `-NoSwitch`, `-NoLogin`, `-Json`; `-TenantId` takes a list `a,b,c` and then registers one context per tenant without switching the active context, logging each new context in by name, AB#6840). The cmdlet looks the installation up by name and builds the service URIs from the configured `services.*` URL templates (`{0}` is substituted with `-$UriSuffix`). See `docs/installations-config.md` for the config schema. Replaces the removed per-environment `Invoke-OctoCliLogin{Local,Production,Staging,Test2}` helpers.

- `Invoke-OctoTenantSweep -CliArguments '-c','<Command>',... (-Installation <i> | -ContextTemplate <t> | -Context <c>) (-Tenant a,b | -AllTenants) [-Exclude ..] [-WhatIf] [-ShowOutput] [-IncludeOutput] [-Json]` - Supported replacement for scripts that copied tokens out of the octo-cli context file (AB#6840). Thin loop around `octo-cli --context <name> -c ...`: one context per tenant (`<inst>_{tenant}`) or one context with `{tenant}` in the arguments; octo-cli does the per-tenant authentication/exchange (AB#6836, octo-cli >= 3.5.27, checked). Result row per tenant (Ok/Denied/Failed, exit code, cause); a denied tenant (not provisioned: `ProvisionCurrentUser -ttid <tenant>`) does not stop the sweep. Never reads, prints, logs or writes a token, never opens the context file, never changes the active context; token-shaped text is scrubbed from all output. `-IncludeOutput` adds the scrubbed stdout per row, e.g. the response of `octo-cli -c GraphQl -tid {tenant} -q ...` (AB#7027), which replaces the GraphQL curl/Python scripts. Tests: `tests/OctoTenantSweep.Tests.ps1`. Details: `docs/tenant-sweep.md`.

### Cluster Access (Rancher / Break-Glass)
Two paths for Kubernetes access to Rancher-managed clusters:
- `Get-RancherKubeConfig -Cluster <name>` - Routine read-only access. Fetches a kubeconfig via the Rancher v3 API using your personal `RANCHER_API_TOKEN` and merges it into `~/.kube/config`. The resulting kubeconfig inherits whatever permissions the token user has. Requires `RANCHER_URL` (populated from `rancher.url` in your octo-tools config, or set in the private profile) and `RANCHER_API_TOKEN` (always set in the private profile, format `token-xxxxx:secret`, created in Rancher UI -> Account & API Keys).
- `Request-BreakGlassKubeConfig -Cluster <name> -Reason "..." -DurationHours <1-4>` - Write access for incidents. Triggers a Semaphore playbook that provisions a short-lived `cluster-admin` ServiceAccount token via Vault response-wrapping, with audit entries in Semaphore, Vault, the K8s audit log, and your operations chat channel. The token TTL closes the window automatically. Requires the `semaphore.*` and `vault.addr` blocks in your octo-tools config (see `docs/installations-config.md`).

This cmdlet pair assumes your clusters do not bind a persistent `cluster-owner` to any AD group — write access goes through the break-glass flow only.

## Project Structure

- `/modules/` - PowerShell modules for all development commands
- `/tests/` - Pester 5 tests (`Invoke-Pester ./tests`; install with `Install-Module Pester -MinimumVersion 5.5 -MaximumVersion 5.99 -Scope CurrentUser`, without `-MaximumVersion` you get Pester 6); they use a fake checkout in `TestDrive` and mock the build step - never run real builds or touch the real NuGet folders from tests

- `/assets/` - Terminal profile assets and logos

## Development Workflow

1. Start infrastructure: `Install-OctoKubernetes` (first time; afterwards the kind cluster keeps running or is started with Docker)
2. Build projects: `Invoke-BuildAll`
3. Start application: `Start-Octo`
4. Make changes and rebuild as needed
5. Clean up when done: `Stop-Octo` (the kind infra keeps running; `Uninstall-OctoKubernetes` deletes it with its data)
